## 已确认并修复：运行时函数未注册

原实现只查找源程序声明过的函数。PDF 第 1–2、7 页定义的运行时函数无需源码声明，
但原实现会把它们报告为 c，导致整个正确程序不输出 `symbol.txt`。
这是语义功能遗漏，不只是符号输出多了几行。

测评机正确样例中的 `day = get_int();`，修复前实际输出 `6 c`。
修复后，符号输出精确匹配官方样例：

```text
1 year ConstInt
1 month ConstInt
1 day Int
1 getDay IntFunc
1 fun IntFunc
2 day StaticInt
5 length Int
```

修复使用独立的 `RuntimeLibrary` 签名表，提供下列类型：

| 名称 | 返回类型 | 形参类型 |
|---|---|---|
| get_int | int | 无 |
| get_char | char | 无 |
| get_string | void | char[]、int |
| put_int | void | int |
| put_char | void | char |
| put_str / put_string | void | char[] |

这些符号参与正常的函数调用检查及 AST 绑定，但不插入用户 Scope，
不输出到 `symbol.txt`，不生成活动记录，不改变全局 1 和后续作用域的编号。
类型错误、参数数量错误仍分别报 e、d；未注册的其它名字仍报 c。

## 关系/逻辑结果类型：按用户指定统一为 int

原始 PDF 第 1 页说关系/逻辑运算得到 0 或 1，并要求计算规则与 C 一致；
第 8 页类型约束第 3 条又说 char 类型之间的运算结果仍为 char，
未明确该条是否只针对算术运算。两种理解在复杂条件上会产生不同结果。

本地 `test/交付/testfile6.txt` 第 13 行：

```c
while (i < limit && text[i] != '\0' && text[i] != '\n') {
```

基线实现（`c2e8d95`）把 `i < limit` 判为 int，把 `text[i] != '\0'` 判为 char，
随后按“不同类型不能混合运算”的规则在 `&&` 报 e。
如果测评机把所有比较/逻辑结果统一为 int，这行就应当合法，基线实现将误报。
如果测评机按第 8 页的文字将 char 比较结果保留为 char，基线实现符合该解释。

本地测试集的 GCC 执行结果不能证明测评机采用哪一种解释，
用户提供的官方样例也没有覆盖这种条件。

2026-10-22，用户反馈运行时修复后测评通过率为 83%，并明确要求尝试将所有比较/逻辑结果统一为 int。
因此在保留基线 commit `c2e8d95` 后，调整了 `SemanticAnalyzer.finishExpression()`：

- `< <= > >= == != && ||` 的结果为 int。
- 一元 `!` 的结果为 int。
- 算术运算及一元 `+/-` 仍保留操作数类型，char 回绕规则保持不变。
- 仍先检查操作数类型，混合基本类型、数组、void 等非法操作不会被结果类型转换掩盖。

新增回归直接检查全部 9 种运算的 int 结果及 0/1 常量值，并覆盖上述复杂条件、
运行时未知条件、逻辑非组合、比较结果再参与比较，以及错误操作数。
本次是依据用户指示进行的测评尝试，不把它写成原 PDF 已经明确的结论；新平台通过率仍待再次测评。
